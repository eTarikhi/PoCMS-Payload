# Phase 1 — GraphQL security status

**Status:** Partial; not production-ready. No public `/api/fgql` endpoint or persisted-query registry is enabled, and this audit authorizes none.

This document separates what was **verified**, by which method, from what remains **unverified**. Do not promote an unverified item to a verified claim without a new executable check.

## Independently verified work

- `POST /api/graphql` authenticates the incoming headers through Payload's `getPayload({ config }).auth(...)` and applies `hasAnyRole`, matching `Users.access.admin`. Unauthenticated requests receive `401`; authenticated users without an Admin-panel role receive `403`. After authorization, a bounded in-process token bucket keyed by the validated Payload `user.id` runs before body reads; rate rejections receive `429`. Missing or malformed authenticated IDs fail closed with `503`. The route then enforces the existing 1 MiB actual-byte cap and a 15-second absolute body-read deadline; oversized bodies receive `413`, while incomplete or aborted uploads receive `408`. Bounded, timely bodies are replayed to Payload's existing `GRAPHQL_POST(config)` handler.
- `/api/graphql-playground` uses the same authorization gate. Payload continues to decide whether the Playground is served in the current environment. GraphQL CORS preflight still uses the existing `REST_OPTIONS(config)` handler.
- The Admin GraphQL inspector still targets `/api/graphql` and includes browser credentials by default. The REST catch-all, `/api/form-submissions`, frontend readers, draft preview, CustomCode, media, Live Preview, and PostgreSQL schema were not changed.
- Route tests exercise unauthenticated rejection, roleless-user rejection, access for a non-Administrator user with an assigned role, fail-closed handling of a missing authenticated ID, body-size enforcement after authorization, Playground protection, and unchanged OPTIONS delegation. Separate no-database rate-limit tests cover token thresholds, identity isolation, spoofed forwarding headers, process-instance scoping, CORS and GraphQL resolver non-execution. Test doubles are used for Payload authentication and the Payload route handler; a separate no-database test executes a small operation with GraphQL.js. These tests do **not** prove real Payload resolver execution or production authentication.
- The existing anonymous-access/schema tests still characterize public reads, restricted fields, the form POST, and the `Mutation.createFormSubmission` surface. No mutation was issued, so form hooks, email, and other side effects were not triggered.

## Request-body limit and GraphQL operation-cost assessment

### Request-body limit

The request path is now explicitly bounded at this route, rather than relying on Next.js's 10 MiB clone/proxy setting:

1. `withPayloadAdminPanelAuthorization` runs first. `payload.auth` receives headers only; unauthenticated (`401`) and roleless (`403`) requests return before the rate check or any body read. The authorized user's identity is passed to the limiter only after the existing Admin-role check succeeds.
2. `withGraphQLRequestRateLimit` runs before `withGraphQLRequestBodyLimit`, so a `429` does not read the request body. Only rate-admitted POSTs enter the body guard.
3. `withGraphQLRequestBodyLimit` reads the stream in chunks and counts each chunk's actual byte length; it never uses `Content-Length`. Its geometrically grown buffer never exceeds **1,048,576 bytes**; zero-length chunks are not retained. One absolute **15,000 ms** deadline starts when body reading begins and is not reset when a new chunk arrives. The first byte beyond the limit returns JSON `413`; an incomplete stream at the deadline returns `408`. On overflow, timeout, or abort, the reader is cancelled without awaiting a client-controlled cancellation promise. The pending read is allowed to settle before the reader lock is released; the timer and abort listener are removed. Growth can briefly retain the prior buffer plus the replacement buffer, and the source has already allocated its current chunk; neither is an unbounded body accumulation.
4. The `413` and `408` responses carry `Cache-Control: no-store`, set `Vary: Origin`, and use Payload's `headersWithCors` with the original request headers and configured CORS options. Other body-stream read failures receive a controlled `400` with the same no-store/CORS handling. Responses delegated to Payload continue to retain existing CORS and `Vary` headers through the Admin wrapper.
5. For accepted bodies, the bounded bytes are reattached to a replacement `Request` with the original URL, method, headers, and signal. The nesting preflight clones that already-bounded request to parse the JSON envelope and lex its `query` before delegating the original request to Payload. This adds one JSON read/parse over a body capped at 1 MiB; Payload then keeps its existing clone, hydration, and graphql-http parsing flow. The preflight does not consume or alter the bytes seen by Payload, and no unbounded body accumulation is introduced.
6. The installed graphql-http 1.23.1 POST parser accepts `application/json` with no charset or `charset=utf-8`; the preflight matches that contract and its `Accept` negotiation. It delegates malformed JSON and non-string/missing query envelopes unchanged for graphql-http's normal client error, delegates unsupported media types/charsets for its normal `415`, and preserves `406` for unacceptable response media types. Its controlled nesting error uses the negotiated JSON response media type. Source inspection and database-free tests confirm that `application/graphql`, form-urlencoded, multipart, and unsupported JSON charsets are not alternate accepted POST encodings that bypass the nesting scan.

The selected 1 MiB threshold is based on the repository's generated Admin documents, not a claim about all external consumers. A no-database evaluation of `documentQuery` for the 32 GraphQL-enabled collection/global entities combined found that the largest generated single-document, depth-5 query takes **248,394 JSON bytes** when serialized as a `{ "query": ... }` body (no per-request variables); the cap is about **4.2 times** that size, leaving roughly 800 kB for variables and other request fields. A client whose complete JSON request exceeds 1 MiB—including large variables, custom documents, or mutation inputs—will now receive 413. External-consumer telemetry is unavailable, so that compatibility risk must be considered before deployment. The Admin's depth-5 generation setting itself is not a server-side GraphQL limit; the independent 1,000-delimiter parser-safety ceiling is documented below.

### Slow-upload deadline and disconnect semantics

The **15-second total wall-clock deadline** begins when the authorized, rate-admitted request enters body reading; it does not reset when chunks arrive and it does not cover authentication, GraphQL parsing, or resolver execution. A stalled or continuously slow upload returns `408`. A request-signal abort and a stream `AbortError` are also classified as `408` (not an application `500`); another body-stream read failure receives a controlled `400`. If the peer has already disconnected, it may not be possible to deliver that response, but the route does not misclassify the expected abort as a server failure. Error responses are no-store and retain configured CORS behavior, and none invokes the downstream GraphQL handler.

On timeout, abort, or overflow the reader is cancelled, but its cancellation promise is deliberately not awaited. When a read is outstanding, cancellation settles the pending read and a cleanup continuation releases the reader lock; the abort listener and total-deadline timer are removed. This prevents an uncooperative source `cancel()` promise from holding the route open. Fake-timer tests cover a never-completing stream whose `cancel()` never settles, a slow trickle that produces two chunks six seconds apart but still hits the 15-second total deadline, an active request-signal disconnect, an `AbortError` stream failure, generic stream-read failure, lock release, and resolver non-execution.

The database-free body suite also covers exact-boundary and over-boundary bytes, misleading/missing/malformed `Content-Length`, normal stream completion and byte replay, overflow cancellation, authorization precedence, CORS/no-store headers, successful delegated GraphQL responses, and unchanged OPTIONS/method dispatch. The nesting suite instruments graphql-http's parse and validate stages, reproduces parser stack errors without a database at 2,500 and 4,000 nested fields, verifies a controlled pre-parse 400 with no resolver execution, measures all generated Admin query documents, and validates a depth-5 Articles Admin query against the application's `configToSchema` schema with execution stubbed. The complexity/cycle suite builds a small in-memory schema through Payload's `configToSchema`, composes Payload's installed rules with graphql-http 1.23.1, and verifies cycle rejection, resolver non-execution, valid fragment reuse, the 1000 threshold, and existing multi-operation behavior. Its 15-level doubling-fragment case reproduced 32,768 estimator calls and actual complexity 32,769 before fragment memoization; the patched visitor preserves the same 400 rejection and score with one estimator call, and still does not invoke the root resolver. A second case verifies that memoized costs are recalculated for each operation when `@include` variables differ. No application resolver or database operation is executed, and no deployed Next.js proxy is exercised.

### Authenticated GraphQL request-rate limit

The POST route explicitly uses Next.js's Node.js runtime and creates one in-memory token-bucket store for each loaded route-module instance. The production policy permits a burst of **120 requests** per authenticated user and refills an empty bucket to 120 tokens over **60 seconds** (2 requests/second at steady state). At most **10,000 active identities** are retained per instance; inactive buckets are swept after their refill window, and newly seen identities are rejected with `429` while the bounded store is full.

The key is the authenticated Payload `user.id`, passed to the limiter only after the existing Admin-role authorization succeeds. Positive safe-integer IDs and non-empty, trimmed strings up to 128 characters are accepted. Missing or malformed IDs fail closed with a generic `503` before the body is read; they do not skip accounting. Client IP and all client-supplied forwarding headers are ignored. Responses do not include or log the identity. A rate rejection is JSON `429` with `Cache-Control: no-store`, `Retry-After` rounded up to at least one second, and Payload's configured CORS headers. OPTIONS preflight remains on `REST_OPTIONS(config)` and is not charged to the POST bucket.

**Distribution limitation:** this is a per-loaded-Node-route-module/worker mitigation, not a distributed quota. Vercel cold starts, multiple workers, and horizontally scaled Docker instances have independent buckets; a user's effective total allowance can multiply across instances, and a new instance starts with a full bucket. The repository has PostgreSQL for application data, but no atomic shared rate-limit store/table, Redis/Upstash/KV, or configured gateway rule. A database-backed counter would add a write/lock to every GraphQL POST and require schema/deployment coordination; no new external service or Neon dependency was introduced. The in-process policy bounds bursts and sustained load per worker but must not be represented as production-grade cross-instance protection. Shared enforcement remains necessary before any public GraphQL endpoint or claim of a global quota.

### Payload's AST complexity rule

Payload 3.90.2 already applies `graphQL.maxComplexity`, whose default is **1000**. This application does not override it. Payload builds the rule from `fieldExtensionsEstimator()` followed by `simpleEstimator({ defaultComplexity: 1 })`; generated relationship and join fields usually carry a static complexity of 10.

The AST rule is a useful coarse selection-size check, but it is not a reliable resolver-work budget. The estimator and resolver observations below come from Payload 3.90.2 source inspection; actual cost against this application's database, hooks, and external clients remains unmeasured:

- The observed 2,500/4,000-field stack failure occurs **before validation**, in GraphQL.js parsing. Installed versions are `graphql@16.14.2`, `@payloadcms/graphql@3.90.2`, `@payloadcms/next@3.90.2`, and `graphql-http@1.23.1`. graphql-http's `createHandler` calls `parse(query)` before it constructs/runs the validation rules; an instrumented database-free handler showed `parse` throwing `RangeError: Maximum call stack size exceeded` at both depths while `validate` was never called. GraphQL.js `Parser.parseSelectionSet` recursively calls `parseSelection` → `parseField` → `parseSelectionSet`; by contrast, GraphQL.js `visit` uses an explicit iterative stack. Thus standard validation rules are not the cause of these particular failures. Payload's `QueryComplexity.nodeComplexity` is also recursive, but it is reached only after parse and was not invoked in these reproductions. In this fresh clone graphql-http converted the parser exception to HTTP 400 at both depths; the earlier empty 500 at 4,000 was not reproducible through this direct Fetch handler, so that exact status remains unverified at the deployed Next.js boundary. Both query strings (20,029 and 32,029 bytes; 7,508 and 12,008 GraphQL tokens) are below the route's 1 MiB body cap. Fresh-process parser probes also show syntax-specific recursion: 1,500-level selection and list variants parsed, but a 1,500-level nested object literal threw `RangeError`; a 1,000-level object literal parsed. The nesting suite reproduces that object-value parser failure and verifies over-limit object/list inputs are rejected before parse.
- GraphQL.js offers a `maxTokens` parser option but no maximum-nesting option. A token ceiling low enough to reject the 2,500-field query (7,508 tokens) would also reject generated Admin documents with up to 9,562 tokens. graphql-http supports a custom parser, but Payload 3.90.2's `GRAPHQL_POST` does not pass that option through. The route therefore uses GraphQL.js's iterative `Lexer` for a bounded pre-parse scan of `{}`, `[]`, and `()` nesting, before delegating accepted requests to the unchanged parser and full standard/Payload validation. The maximum is **1,000 nested delimiters**, equal to the existing complexity threshold and far above measured Admin usage. Over-limit documents receive a GraphQL-shaped HTTP 400 before parse, validation, or resolver execution; exactly 1,000 delimiters remain accepted for a query whose score is exactly 1,000.
- Before selecting that ceiling, the custom Admin GraphQL `documentQuery` generator was evaluated across its 32 enabled collection/global documents at all six supported depth settings (192 documents total). Maximum actual selection-set and delimiter nesting was **15** (Redirect at requested depth 5); the depth-5 Article query used in the regression is a valid **10** levels deep. Generated documents reached 9,562 tokens and 240,046 query bytes (248,394 bytes as a JSON body). The 1,000-level guard is more than 66 times the measured maximum, while nested field chains beyond it already exceed the application's default field-cost budget. This is a syntactic parser-safety bound, not an estimator or database-cost model; unusually nested custom argument/inline-fragment structures beyond it are intentionally rejected.
- Each alias is visited and charged separately. Acyclic fragment costs are still added at every spread, but the checked-in patch now memoizes the calculated fragment complexity per operation so the same fragment subtree is not re-expanded repeatedly. The memo is reset for each operation because variable values and `@include`/`@skip` decisions may differ. Variables are supplied to the rule for coercion and those directives, but the installed estimators do not use list arguments such as `limit` to multiply cost.
- Payload assigns relationship and join fields a static complexity of **10** by default (field-level `graphQL.complexity` can override it); the score is not multiplied by result count or parent-list cardinality. Static source tracing shows that the top-level collection `find` resolver forwards `limit`/`pagination` to `findOperation`: pagination defaults on with limit 10, but `pagination: false` or `limit: 0` becomes a zero limit, which the Postgres adapter converts to no SQL `LIMIT`. The GraphQL join resolver is looser: an omitted/non-positive join `limit` becomes zero and, unless `count: true`, it calls `find` with pagination disabled, so it can return all matching join rows by default. A `hasMany` relationship resolver schedules DataLoader lookups for each stored related ID; DataLoader batches and deduplicates loads, but the resulting record and nested-field fan-out depends on actual relationship cardinalities and database data. No row counts, SQL plans, query latency, or resolver work were measured. Consequently, the configured complexity score of 1000 is not a bound on rows returned, relationship fan-out, hook work, access checks, database selectivity, or arbitrary custom resolver work.
- `src/payload.config.ts` declares no custom `graphQL.queries` or `graphQL.mutations`; its GraphQL customization here is validation-only. The query/mutation fields therefore come from Payload's generated collection/global and plugin schemas, but generated resolvers still call Payload APIs and plugin logic. Application-source inspection (not execution) found that `Users.permissions` runs the `computePermissions` field `afterRead` hook, which loads missing role documents through a batched Local API `find` and uses request-local plus 15-second per-Payload caches. `Articles`/`Projects` have mutation hooks for validation, read-time/static-image metadata, and cache revalidation; media, form-submission, and inbox hooks can also do image processing, validate submissions, write inbox records, update thread rollups, or publish events. These are possible operation costs/side effects, not measured timings; the regression suite stubs execution and does not run resolver, database, email, image, or hook behavior.
- The rule receives variables but not the selected `operationName`. Its implementation visits and accumulates complexity for every operation definition in a document, so an unused expensive operation can cause a selected cheap operation to be rejected (a compatibility false positive), though this behavior does not provide a limit bypass.
- Production introspection is already disabled by Payload's default and this config's `NoProductionIntrospection` validation rule (`__schema`/`__type`). That does not bound ordinary resolver execution.
- In the unpatched Payload 3.90.2 package, a no-database reproduction with GraphQL 16.14.2 showed that a cyclic spread made the recursive complexity visitor throw `RangeError: Maximum call stack size exceeded`. graphql-http 1.23.1 appends Payload's rule to GraphQL.js `specifiedRules` (which include `NoFragmentCyclesRule`), but GraphQL.js runs the rules in a combined visitor and reporting an error does not stop other rules. Payload's `OperationDefinition` visitor recursively expands spreads and can throw during that same validation pass, so validation-rule ordering alone cannot protect it. The exception escapes validation and graphql-http's Fetch adapter returns an empty HTTP 500.
- The checked-in pnpm patch for `@payloadcms/graphql@3.90.2` tracks fragment names on the active recursion path, skipping only a spread that would re-enter that path, and memoizes each computed fragment cost within one operation. The same active path is threaded through fields and inline fragments and cleaned up on return, preserving the cycle guard; cache entries are cleared before each operation so variable-dependent directives are recalculated. Every non-cyclic spread still adds the cached score, so valid fragment reuse keeps its prior complexity result without repeated subtree traversal. The standard `NoFragmentCyclesRule` remains enabled and returns the client validation error; invalid documents do not reach execution. With `Accept: application/graphql-response+json`, graphql-http returns HTTP 400. The patch preserves Payload's estimator and 1000 threshold, and is not a resolver-work budget or a bound on deeply nested field selections.
- The selected-cheap plus unused-expensive two-operation case is also covered: Payload 3.90.2 does not pass `operationName` into its complexity rule and accumulates scores across all operation definitions, so the expensive unused operation still rejects the document. This existing compatibility behavior is intentionally unchanged.

**Recommendation:** keep Payload's existing default complexity threshold of 1000 unchanged and do not claim it prevents expensive resolver operations. The checked-in package patch memoizes per-operation fragment complexity while preserving cycle detection and charging every spread; the reproduced 15-level DAG still scores 32,769 and is rejected before resolver execution, but estimator calls fall from 32,768 to one. The route now also rejects GraphQL documents with more than 1,000 nested lexical delimiters using an iterative lexer before GraphQL.js parsing; this limit is backed by the measured Admin maximum of 15 and leaves standard parser and validation behavior unchanged below the ceiling. Do not add a home-grown resolver-cost estimator or arbitrary list/alias limits here. A resolver-aware policy would need to account for collection limits, nested relationships and hook costs. The size and nesting caps do not bound resolver work that fits within them. The total body deadline limits slow uploads after authorization; the token bucket limits authenticated request rate per loaded route instance but cannot cover authentication cost or aggregate traffic across instances. These measures are layered mitigations, not production-grade global DoS protection.

## Unverified — external consumers

**External `/api/graphql` consumer compatibility remains UNVERIFIED.**

- Vercel telemetry and request logs are **inaccessible**: the Vercel connector is disconnected and no deployment telemetry credentials are present in this environment.
- Repository inspection does **not** establish whether external clients depend on GraphQL. The only in-repository references are documentation (`README.md`, `docs/api.md`, `docs/getting-started.md`, `docs/project-structure.md`), the Admin GraphQL inspector and DevTools links, this session's tests, and lockfile dependency entries. Those references describe and consume the route from inside the product; they say nothing about third-party or out-of-repository clients.
- The new Admin gate is therefore **incompatible with any anonymous client that may exist**. Absence of evidence is not evidence of absence: do not treat the repository search as proof that no external consumer exists.
- Inventory and approval of external consumers must happen before deployment. This audit does not and cannot supply that approval.

## Blockers before public GraphQL or deployment

1. **External `/api/graphql` consumers are unknown.** See the unverified section above; the gate must be reconciled with real consumer inventory before release.
2. **No disposable PostgreSQL instance is available.** Docker, Podman, PostgreSQL tools, a listener on port 5432, and `POSTGRES_URL`/`DATABASE_URL` are unavailable. Payload 3.90.2 request initialization, anonymous resolver access, and GraphQL execution have not been tested against a real request/database. `docker-compose.yml` defines `postgres:16-alpine`, but it cannot be started in this environment, and no integration result is claimed.
3. **Do not mount `GRAPHQL_POST(config)` directly at `/api/fgql`.** The installed Payload 3.90.2 request initializer classifies a request at that non-configured path as REST (`isGraphQL: false`, `payloadAPI: 'REST'`). The adapter and its request-context/execution tests remain unimplemented and **unverified**. Therefore `/api/fgql` is intentionally absent.
4. **No public operation allowlist exists.** Do not accept public query text or enable a public route until the real request-context proof is complete and a server-controlled exact SHA-256 allowlist has executable rejection tests. `createFormSubmission` remains a potential anonymous side-effect mutation on the current broad GraphQL schema; it was inspected statically but never executed.
5. **Shared rate limiting is unverified.** The existing Admin POST has only a process/route-instance token bucket; no shared rate-limit backend or supported gateway protection has been demonstrated. There is no distributed-quota claim. Shared enforcement remains a release blocker for any future public GraphQL endpoint or global quota requirement.

## Scope explicitly authorized by this audit

- Admin-gating the existing `POST /api/graphql` and `GET /api/graphql-playground` only.
- Enforcing the process-scoped authenticated-user rate limit, 1 MiB actual-byte body cap, 15-second total body-read deadline, and 1,000-delimiter iterative nesting preflight on the existing authorized JSON GraphQL POST only; OPTIONS, method dispatch, standard/Payload validation, and unrelated REST routes remain unchanged.
- Regression coverage proving unsupported methods cannot execute GraphQL and cannot bypass the gate, and that over-limit documents reject before parsing or resolver execution.

Nothing else. This audit does **not** authorize a public GraphQL endpoint, an anonymous persisted-query endpoint, an anonymous GraphQL route, or any change to REST, form-submission permissions, Payload access policies, the GraphQL schema, or generated artifacts.
