# PoCMS admin UI guide

How the customised Payload admin is put together and how to extend it. The decisions behind it are
in [`adr/`](./adr/README.md); the original analysis and roadmap are in
[`shadcn-payload-ui-analysis.md`](./shadcn-payload-ui-analysis.md) (a historical record: its file
paths predate [ADR 0009](./adr/0009-payload-native-component-layout.md)).

The admin is still Payload's admin (Payload 3.9x). Nothing replaces Payload's routing, forms, list
state or access control. The work adds four layers on top:

1. **Design tokens** that restyle Payload's own UI (colours, type, radius, dark theme).
2. **An isolated Tailwind v4 build** (`acn:` prefix, no Preflight) for the custom components.
3. **Elements**: accessible building blocks on Base UI, in `src/components/admin/elements`.
4. **Custom components in Payload's slots**: branding, header actions, navigation, dashboard
   widgets, the TanStack list view, field components and cells, one-document collections and roles.

## Structure

The custom components live in `src/components/admin`, in folders named after the places Payload's
documentation defines for custom components
([overview](https://payloadcms.com/docs/custom-components/overview)). Every component, file by
file, is listed in [`src/components/admin/README.md`](../../src/components/admin/README.md).

| Folder (`src/components/admin/`) | Registered at | Payload docs |
| --- | --- | --- |
| `graphics/` | `admin.components.graphics.Logo`, `.Icon`; `admin.avatar` | [Root Components](https://payloadcms.com/docs/custom-components/root-components) |
| `providers/` | `admin.components.providers` | [Custom Providers](https://payloadcms.com/docs/custom-components/custom-providers) |
| `actions/` | `admin.components.actions` (header) | [Root Components: actions](https://payloadcms.com/docs/custom-components/root-components#actions) |
| `nav/` | `beforeNavLinks`, `afterNavLinks`, `logout.Button` | [Root Components](https://payloadcms.com/docs/custom-components/root-components) |
| `views/` | `admin.components.views.*`; a collection's `views.list.Component`, `beforeListTable` | [Custom Views](https://payloadcms.com/docs/custom-components/custom-views), [List View](https://payloadcms.com/docs/custom-components/list-view) |
| `widgets/` | `admin.dashboard` (`widgets/config.ts`) | [Dashboard Widgets](https://payloadcms.com/docs/custom-components/dashboard) |
| `fields/` | a field's `admin.components.Field`, `.Cell` | [Field components](https://payloadcms.com/docs/fields/overview#custom-components) |
| `elements/`, `hooks/`, `utilities/` | not registered (the folder names Payload's own UI package uses) |  |

Component Paths in the config are relative to `admin.importMap.baseDir` (`src`), for example
`/components/admin/actions/ThemeToggle#ThemeToggle`; a folder resolves to its `index.tsx`. Each
component has its own PascalCase folder with `index.tsx` as the entry and its parts beside it
(`Menu.tsx`, `Chart.tsx`, `data.ts`); field folders hold `Field.tsx` and `Cell.tsx`.

Outside that folder:

| Path | What it is |
| --- | --- |
| `src/styles/admin/admin-ui.css` | Stylesheet entry: Tailwind v4 `prefix(acn)`, theme bridge, scoped reset |
| `src/styles/admin/tokens.css` | Tier 0-2 design tokens, defined from Payload's variables |
| `src/styles/admin/variants.css` | Custom variants the elements use (`data-open`, `data-closed`, …) |
| `src/styles/admin/payload-overrides.css` | The few overrides of Payload classes |
| `src/styles/admin/nav-icons.css` | Sidebar icons, generated by `pnpm generate:nav-icons` |
| `src/styles/admin/nav-rail.css`, `responsive.css` | Icon rail and theme animation; responsive and touch fixes |
| `src/plugins/adminUI.ts` | Gives every collection the list view, list summary and checkbox cell |
| `src/endpoints/*` | Admin endpoints: site cache, migrations, developer tools |
| `src/access/permissions.ts`, `src/access/roles.ts`, `src/access/singleton.ts` | Permission checks (client-safe), access functions and role hooks, one-document create access |

The **component gallery** at **`/admin/gallery`** (Developer tools capability) shows all of it inside Payload's
shell: a registry of every registered component, read from the running config, then the graphics,
the dashboard widgets with your data, the list summary, the field components inside a Payload form,
every cell with sample values, and finally the elements and design tokens.

## Design tokens

`tokens.css` is layered in tiers, all inside `@layer payload` (ordered after Payload's own
`payload-default` layer, so no `!important` is needed):

- **Tier 0, brand primitives**: the site's amber and navy, in hex (the contrast script parses them).
- **Tier 1, Payload theme variables**: what Payload's own UI reads. We set `--font-body` (Inter),
  `--style-radius-s/m/l` (6/8/12 px), the focus outline, in light mode a warm off-white page
  (`--theme-bg: #f7f6f3`) with faintly tinted elevation steps 50–300 (ADR 0010: surfaces such as
  inputs, cards, popups and tables stay white), and in dark mode a navy-tinted
  `--theme-elevation-*` scale.
- **Tier 2, semantic tokens** (`--background`, `--foreground`, `--card`,
  `--popover`, `--primary`, `--secondary`, `--muted`, `--accent`, `--destructive`, `--success`,
  `--warning`, `--border`, `--input`, `--ring`, `--chart-1..5`). They are defined _from_ Payload's
  variables, so the elements follow Payload's theme switch automatically.
- **Tier 3, Tailwind utilities**: the `@theme inline` block in `admin-ui.css` maps Tier 2 onto
  `acn:*` classes (`acn:bg-card`, `acn:text-muted-foreground`...).

Light and dark values live side by side (`[data-theme='dark']`). The theme switch (header button
or account page) toggles both Payload and the custom components.

`payload-overrides.css` holds the few rules that target Payload's own classes: brand-coloured
primary buttons, field descriptions and sidebar group headings in `--muted-foreground` (Payload's
grey is under 3:1, found by the gallery's axe test), the sign-in screens' faint amber glow and
tabular figures in lists.

Change the brand colour by editing the Tier 0 amber values, then run `pnpm check:contrast`: it
checks 34 foreground/background pairs against WCAG AA in both themes and fails CI if one drops
below the threshold. Warning colours never carry meaning alone; they always come with an icon and
a label.

**Spacing** follows Payload's scale: Tailwind's `--spacing` is `calc(var(--base) / 5)` = 4 px, so
`acn:p-5` equals Payload's `--base` (20 px). Payload's root font size is 13 px; Tailwind sizes are
expressed against it through the theme bridge, so `acn:text-sm` matches Payload's body text.

### Payload 4 readiness

Payload 4 replaces the Sass variables with its own semantic tokens. Only Tiers 1 and 2 reference
Payload's names, so an upgrade means re-pointing these lines; components use Tier 2/3 and don't
change. Current mapping (light / dark where they differ):

| Our token (Tier 2)        | Defined from (Payload 3)                                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `--background`            | `--theme-bg`                                                                                                       |
| `--foreground`            | `--theme-text`                                                                                                     |
| `--card`, `--popover`     | `--theme-elevation-0` / `--theme-elevation-50`                                                                     |
| `--muted`                 | `--theme-elevation-50`                                                                                             |
| `--muted-foreground`      | `--theme-elevation-600` (Payload flips the scale in dark mode)                                                     |
| `--secondary`, `--accent` | `--theme-elevation-100`                                                                                            |
| `--border`, `--input`     | `--theme-elevation-150`                                                                                            |
| `--primary`               | Tier 0 `--brand-amber-700` / `--brand-amber-500` (Payload's primary button is restyled in `payload-overrides.css`) |
| `--destructive`           | `--theme-error-*`                                                                                                  |
| `--success`               | `--theme-success-*` (Payload's blue scale)                                                                         |
| `--warning`               | `--theme-warning-*`                                                                                                |

Tier 1 values we set on Payload itself: `--font-body`, `--style-radius-s/m/l`, the dark
`--theme-elevation-*` scale and the focus outline.

Other v4 notes: run `npx @payloadcms/codemod`, check the renamed admin component keys, and plan for
the new defaults (`overrideAccess: false` in the Local API, which our widgets already use).

## Tailwind in the admin

- Every utility carries the **`acn:` prefix** (`acn:flex acn:gap-2`), so Tailwind classes can't
  collide with Payload's class names (`.table`, `.container`, `.btn`...). Tailwind v4 only accepts
  a letters-only prefix used as a variant, hence `acn:` rather than `acn-`.
- There is **no Preflight**. A small reset applies only to elements with a `data-slot` attribute
  (the elements); Payload's markup is untouched.
- Tailwind scans only `src/components/admin` (`@source` in `admin-ui.css`). Classes written
  elsewhere are not generated.
- `pnpm check:tw-prefix` parses every admin file (TypeScript AST: `className`, `cn()`, `cva()`
  including variants and compound variants) and fails on unprefixed utilities.
- `cn()` merges prefixed classes correctly (`extendTailwindMerge({ prefix: 'acn' })`).
- Prettier sorts admin classes (`prettier-plugin-tailwindcss`, admin files only).
- The dev server caches class candidates. After fixing an invalid class (for example an unquoted
  attribute selector), restart `pnpm dev` if the old CSS error persists.

## Adding a component

1. **Pick the slot** in Payload's docs and create the file in the matching folder:
   `src/components/admin/<folder>/<Name>/index.tsx`, or `fields/<Name>/Field.tsx` / `Cell.tsx` for
   a field. Write a Server Component unless it needs state or browser APIs; then add
   `'use client'` and keep its props serializable.
2. **Register it** with its Component Path: for example
   `actions: ['/components/admin/actions/MyAction#MyAction']` in `payload.config.ts`, a field's
   `admin.components.Cell`, or an entry in `widgets/config.ts`.
3. **Regenerate the import map** with `pnpm generate:importmap` (`pnpm generate:all` after field
   or widget changes, since widget slugs are typed). CI fails on a stale import map.
4. **Keep it light.** Payload's admin is one route, so every client component reachable from the
   import map ships to every admin page: register a small wrapper and load the heavy part from a
   sibling file with `next/dynamic` or `React.lazy` (see [Bundle size](#bundle-size)).
5. **Check it in the gallery.** It appears in the registry by itself; add a live preview to
   `views/Gallery/previews.tsx`, so the gallery's axe test covers it in both themes.
6. Run `pnpm typecheck && pnpm lint && pnpm check:tw-prefix` and add an e2e test for what it does.

### Adding an element

Elements are plain components in `src/components/admin/elements/<Name>/index.tsx`, built on
`@base-ui/react` where behaviour is involved (popups, focus, form controls). There is no generator:
write the element, or adapt upstream code by hand, give its parts a `data-slot` (the scoped reset
applies to those), prefix every class with `acn:` and run `pnpm check:tw-prefix`. Prefixing by hand
tends to miss quoted attribute selectors (`[stroke='#ccc']`), class names used as object keys
inside `cn()`, and `compoundVariants`. Add a demo to `views/Gallery/Elements.tsx`.

Base UI notes: a `Button` rendered as a link needs `render={<a />}` and `nativeButton={false}`;
`Select` needs `items` to show labels in the trigger; `ToggleGroup` values are arrays; a Base UI
checkbox is a `span[role=checkbox]`, so name it with `aria-labelledby` or `aria-label`.

## Navigation and branding

- `graphics.Logo` (login) and `graphics.Icon` (breadcrumb) use the site's favicon set.
- `admin.meta` sets the `· PoCMS` title suffix and the icons.
- Sidebar groups come from `admin.group`: **Content** (Articles, Projects, Media), **Profile**
  (the résumé sections in home-page order, Services included), **Site settings** (the Header
  collection, the Footer global, and the Navigation and Site settings globals) and **Admin**. Payload orders groups by first appearance,
  collections before globals, so the collection order in `payload.config.ts` sets the group order.
- `beforeNavLinks`: the **Create** control lists only collections the user may create. It is a
  native disclosure (`details`/`summary`) holding links, closed by Escape or an outside click.
- `afterNavLinks` (`nav/NavExtraLinks`): **View site** (`NEXT_PUBLIC_SITE_URL`, or the same
  origin) and, with the Developer tools capability, the **Component gallery**. The **Database**
  link follows it, registered by the database tools plugin (`nav/DatabaseNavLink`) rather than by
  `NavExtraLinks`, so the plugin stays portable.
- No `settingsMenu` (gear) and no sidebar log out (`logout.Button` is `nav/HiddenLogout`): the
  site cache refresh is in the developer tools menu and log out in the account menu, both in the
  header. `POST /api/revalidate-site` (`src/endpoints/revalidateSite.ts`) expires the `portfolio`
  cache tag at once (`expire: 0`); saves only mark it stale.
- `actions` (header, rendered right to left): the command menu button, **developer tools** for
  admins, the light/dark switch (`actions/ThemeToggle`, Payload's `useTheme`) and the **account
  menu** (`actions/AccountMenu`: name, email, role, Account settings, Log out), which replaces
  Payload's avatar link (hidden in `nav-rail.css`).
- Developer tools (`actions/DevTools`: `index.tsx` on the server, `Menu.tsx` on the client),
  for roles with the Developer tools capability. A
  **GraphQL Playground** button (where Payload serves it; production blocks introspection, so its
  schema docs only load in development) and a bug-icon menu whose items depend on the environment.
  A badge shows it: Development, Production build, or Vercel's environment and commit.

  | Item | Development | Production build / deployment |
  |---|---|---|
  | Refresh site cache (`POST /api/revalidate-site`) | yes | yes |
  | Purge all cached pages (`POST /api/purge-pages`, `revalidatePath('/', 'layout')`) | yes | yes |
  | Migration status (`GET /api/migration-status`: migrations recorded in this database) | yes | yes |
  | This page, My permissions, Signed-in user (REST JSON); Payload docs | yes | yes |
  | Reset bundler cache (`POST /api/reset-bundler-cache`) | yes | no: the build is immutable |
  | Restart dev server (`POST /api/dev-restart`: touches `next.config.ts`, the page reloads when the server is back) | yes | no: the platform runs the server |
  | Create migration (`POST /api/dev-migrate?name=`: `payload migrate:create --skip-empty`) | yes | no: write migrations in development, deployments run `payload migrate` |
  | Generate (below) | yes | no: generated code is part of the build |

  Development-only endpoints return 404 in production, and every endpoint requires an admin.
  `src/migrations` is git-ignored in this repository, so created migrations stay local until that
  changes.
- **Generate** (same menu, development only): buttons for each code generator (Types, Import map,
  DB schema, GraphQL schema: `node scripts/generate.mjs <target>`; Nav icons:
  `node scripts/generate-nav-icons.mjs`) and **Run generate:all**, through
  `POST /api/dev-generate?target=…` (`src/endpoints/devGenerate.ts`): Developer tools capability, a fixed list of
  targets, one run at a time, output tail in the response and the run's result in the menu. Use it
  after changing collections or admin components instead of a terminal; the dev server picks up the
  regenerated files.
- One sidebar control (`nav/SidebarToggle`: `index.tsx` → `Button.tsx`, `beforeNavLinks`): on
  desktop it sits at the top of the sidebar (top-right corner, or centred above the icons in the
  rail) and collapses the sidebar to the icon rail and back; Payload's own toggler, which only hid
  the whole sidebar, is hidden there, and a sidebar closed by an older preference is reopened. Below
  1025px Payload's toggler is the mobile menu button and ours is hidden. The Next.js dev indicator
  sits at the bottom right (`devIndicators` in `next.config.ts`).

### Site settings, navigation and maintenance

Two globals live in **Site settings**, both saved through `payload.updateGlobal` and both read by the
public site from the `portfolio` cache tag, so a save refreshes the pages immediately
(`portfolioAfterChange` → `revalidatePortfolio`).

- **Navigation** (`/admin/globals/navigation`, `src/globals/Navigation.ts`): a brand and two link
  lists. `primaryLinks` render left of the brand on wide screens and `secondaryLinks` right of it;
  the brand sits in the middle (the same split as the original Bootstrap bar). `newTab` renders a
  plain anchor with `rel="noopener noreferrer"` instead of a `next/link`.
  `mapNavigation()` falls back **per side** to the original links in `DEFAULT_NAVIGATION`
  (`src/app/(frontend)/lib/mappers.ts`) when a side is empty, so a fresh database still has a bar,
  and saving only one side does not wipe the other. A unit test keeps the seed
  (`src/seed/navigation.ts`) and the fallback identical.
- **Site settings** (`/admin/globals/site-settings`, `src/globals/SiteSettings.ts`): `siteName`,
  `supportEmail` and the **maintenance** group. While *Show the maintenance page* is on, the public
  layout renders `components/layout/MaintenancePage.tsx` instead of the route's content on every
  public page (home, articles, not-found). `/admin` and the REST API are in another route group and
  keep working, which is the point: the switch lives in the admin, so an editor can always turn it
  off. The title and message fields only show while the switch is on; the support address becomes
  the page's **Email us** button. `mapSiteSettings()` supplies the same defaults for an unsaved
  global, and a never-saved global is offline (`enabled: false`).

Both are seeded by `pnpm seed` and their schema is migration `20261020_223003_navigation_and_site_settings`.
The e2e spec `tests/e2e/site-settings.e2e.spec.ts` covers the seeded bar and the full maintenance
round trip through the admin form (including the admin staying reachable), and resets the switch
through the API even when a test fails.

Note for tests: the template hides the bar at the top of the page
(`.navbar.fixed-top { display: none }` in `main.css`) and reveals it with the `d-flex` class after
300 px of scroll, so a navigation assertion has to scroll first — a hidden `nav.navbar` in Playwright
is expected, not a regression.

### Command menu

- **Ctrl+K / Cmd+K** anywhere in the admin, or the **Search…** button in the header
  (`actions/CommandMenu/index.tsx`, the only part on every page). The menu itself
  (`actions/CommandMenu/Menu.tsx`) is a separate chunk, fetched when the pointer reaches the button or on
  the first shortcut.
- Groups: **Recent** (documents and globals you opened, kept in localStorage, named from the edit
  view heading), **Go to** (dashboard, every collection and global you can see, account, component
  gallery with the Developer tools capability), **Create** (collections you may create in), **Documents** (title search) and
  **Actions** (theme, sidebar, refresh site cache, view site, log out).
- Document search: two or more letters search each readable collection's `useAsTitle` field over
  REST with the user's own access (`like`, four hits per collection, debounced, stale requests
  aborted). Collections titled by `id` are skipped.
- Ranking (`actions/CommandMenu/match.ts`): prefix beats word start beats substring, every query word must
  match the label or a keyword, accents and case are ignored. With a query, the group holding the
  best match comes first, so Enter runs the most likely command.
- Accessibility: Base UI dialog; the input is an ARIA combobox controlling a grouped listbox
  (`aria-activedescendant`); arrow keys move, Enter runs, Escape closes. Covered by axe in
  `tests/e2e/command-menu.e2e.spec.ts`.
- To add a command, add an item to the list in `actions/CommandMenu/Menu.tsx` (group, label,
  keywords, icon, `run`).

### Keyboard shortcuts

- **Ctrl+K / Cmd+K**: command menu (always on). **/**: command menu. **?**: shortcuts help.
  **G then a letter**: go to a page (D dashboard, A articles, P projects, S services, M media,
  E experiences, K skills, C certificates, U users; only pages the user can see). Payload's own
  Ctrl+S / Cmd+S saves.
- Single-key shortcuts never fire while typing (inputs, editors, comboboxes) or while a dialog is
  open, and the help dialog has a switch to turn them off, stored in localStorage (WCAG 2.1.4,
  Character Key Shortcuts).
- Defined in `actions/CommandMenu/shortcuts.ts`; the listener lives in the trigger (`index.tsx`),
  the help dialog (`ShortcutsDialog`) in the lazily loaded menu chunk.

### Theme switch animation

Switching the theme (header button or command menu) spreads the new theme as a circle from the
button, with the View Transitions API (`utilities/themeTransition.ts`, styles at the end of
`nav-rail.css`). Browsers without the API, and users who prefer reduced motion, get an instant
switch.

### Sidebar icons and the icon rail

- Every sidebar link gets a Lucide icon as a CSS mask, keyed to Payload's nav ids (`#nav-<slug>`,
  `#nav-global-<slug>`). Payload's nav markup is untouched. The icons are generated:
  add the collection or global to `NAV_ICONS` in `scripts/generate-nav-icons.mjs` and run
  `pnpm generate:nav-icons` (part of `generate:all`, so CI catches a stale
  `src/styles/admin/nav-icons.css`). Links without an entry get a generic file icon.
- Group headings (Content, Profile, Site settings, Admin) have icons too (`NAV_GROUP_ICONS`, matched by
  Payload's `#nav-group-<label>`). In the rail they stay as icon buttons that still collapse and
  expand their group, with the group name as a tooltip and a dimmed icon while collapsed.
- Each entry also names a tone (amber, orange, rose, violet, blue, teal, green, slate): theme
  tokens `--nav-tone-*` in `tokens.css` with a light value (700 shade, amber is the brand primary)
  and a dark value (400 shade), so icons keep 3:1 contrast in both themes.
- The sidebar control (desktop, 1025 px and up) shrinks the sidebar to a 4rem icon rail and back;
  smaller screens keep Payload's overlay menu. The state is a cookie (`pocms-nav-rail`), so the server renders the rail directly on the
  next visit, and a `data-nav-rail` attribute that `nav-rail.css` reads with `:has()`.
- In the rail, labels are hidden visually only (links keep their accessible names), the group
  headings become icon buttons, and hover or keyboard focus shows a tooltip with the label. Create becomes an icon and its menu opens to the right.
- Payload marks the _closed_ sidebar `inert`, which is why the rail is a width mode of the open
  sidebar rather than a styled closed one.

### Article Live Preview

- Articles set `admin.livePreview.url` and `admin.preview` to `/preview/articles/<slug>`, but only
  for articles that have a page (slug and body, `hasArticlePage`). The others have no preview. See
  [Live Preview](#live-preview) for why the preview is its own route rather than the article page.
- `ArticleLivePreviewSwitch` (a few hundred bytes) checks whether the page runs inside a frame;
  only then does it load `ArticleLivePreview` (`@payloadcms/live-preview-react`) as a separate
  chunk, which renders the editor's unsaved form state. Public visitors download none of it.
- The live renderer needs the saved document's `id` (Payload resolves the draft's cover image
  for it), which is why the article view model includes `id` and why the preview URL carries it.

## Translations

Every string this repository adds to the admin lives in `src/i18n/en.ts`, in its own namespaces
(`widgets:pageSpeed`, `imageSource:usesUrl`, `pagination:next`, …). Payload's interface translations
are untouched: `src/i18n/index.ts` spreads them and merges ours on top, and `payload.config.ts`
passes the result as `i18n`.

**Keys have no dots.** Payload's `t` splits on the first colon and looks the rest up as a single
property, so `t('custom:widgets.pageSpeed')` always misses (Payload logs `key not found` and renders
the key). One flat level per namespace is the shape that resolves; the i18n test fails on a dotted
key.

- **Config labels** (dashboard widget labels, widget field labels and their options) use
  `customLabel('custom:…')` from `src/i18n/labels.ts`. A label function is resolved per request by
  Payload's `t`, so a language switch would apply immediately; the helper exists because Payload's
  `t` type only knows its own keys and this version has no augmentation hook.
- **Client components** call `useCustomT()` (`src/i18n/useCustomT.ts`), the same narrowing for the
  `useTranslation()` hook.
- **Coverage.** `tests/int/i18n.int.spec.ts` scans `src` for every key of our namespaces and fails if
  one is not in the catalogue, so a missing string cannot reach a screen. Add a language by adding
  `src/i18n/<lang>.ts` and an entry in `i18nConfig`; no component changes.

## Dashboard widgets

Widgets are server components in `src/components/admin/widgets/<Name>/`, registered in
`widgets/config.ts` (`admin.dashboard`). Users can rearrange, resize, remove and re-add them; layouts are saved in
their preferences, and `defaultLayout` applies until they change it.

To add a widget:

1. Write a server component in `widgets/<Name>/index.tsx` that receives `WidgetServerProps`
   (`req`, `user`, `permissions`, `widgetData`). Query through `req.payload` with `req` and `overrideAccess: false`.
2. Wrap the content in `WidgetCard` (`elements/WidgetCard`), or give the root
   `data-dashboard-widget` for the axe test.
3. Add it to `widgets` (and to `defaultLayout` if everyone should see it). Use `fields` for
   per-instance settings, as the **Content count** widget does for its collection.
4. Run `pnpm generate:types` (widget slugs are typed) and `pnpm generate:importmap`, and add a
   preview to the gallery (`views/Gallery/previews.tsx`).

### Count cards

Each count card (`widgets/ContentCount`) shows the total, the additions in the last 30 days and a sparkline
of additions per month over the last year: a server-rendered SVG (no client JavaScript), drawn
with `--chart-1`, decorative because the numbers beside it say the same.

### Publishing chart

`widgets/PublishingActivity/index.tsx` (server) counts articles by `publishedAt` and projects by
`createdAt` over the last 24 months and hands the months to `ChartLazy.tsx`, which loads
`Chart.tsx` with `React.lazy` only when the widget renders. Until then, and on the server, the same numbers show as
plain HTML bars, so there is no empty frame. The chart is plain React and CSS: a Recharts version
cost about 118 kB (gzip) on the dashboard, this one is a few kB.

- **Range:** 6, 12 or 24 months, remembered in localStorage (`pocms-publishing-range`).
- **Series:** Articles and Projects toggle buttons with totals for the range; at least one stays
  on. Series, colours and date fields live in `widgets/PublishingActivity/data.ts`.
- **Tooltip** on hover and on keyboard focus, with the month and both counts.
- **Selected month:** the latest month with activity, or the bar you click, or the one you reach
  with the arrow keys or the Previous/Next buttons. Its axis label turns into a pill, and the
  counts below link to the list filtered to that month (`monthListURL`, a `where` on the series'
  date field).
- **Accessibility:** the months are a radio group with roving focus (arrow keys, Home, End), each
  named with its counts ("December 2024: 2 articles, 0 projects"); the month details are announced
  politely; a visually hidden table links every month. The range buttons' names start with their
  visible text (WCAG 2.5.3). Bar transitions are off with reduced motion.
- To add a series, add it to `PUBLISHING_SERIES`, count it in the widget and add the field to
  `PublishingPoint`.

### Page speed

`widgets/PageSpeed` shows what [pagespeed.web.dev](https://pagespeed.web.dev) shows for the public
site, from `src/integrations/google.ts`:

- **Lab test:** a Lighthouse run through the PageSpeed Insights API, with the performance,
  accessibility, best practices and SEO scores and the lab metrics (FCP, LCP, TBT, CLS, Speed
  Index) in PageSpeed's colours and shapes. A run takes 10–40 s, so it streams in behind a
  placeholder (`<Suspense>`) and the rest of the dashboard doesn't wait. The result is kept for a
  day in Next's data cache (`unstable_cache`, tag `pagespeed`); after that the next visit shows it
  and runs a fresh test in the background. Failures are not kept, and visits during a run share
  it.
- **Real users:** Core Web Vitals of Chrome users from the Chrome UX Report API (p75, the share of
  good, needs improvement and poor loads, the 25-week trend), kept 12 hours. Small sites have no
  record, and the widget says so; the lab test works without one. When phones (or desktops) alone
  have too little data, all devices together are shown.
- **Widget setting:** Phones (Lighthouse on mobile), Desktops (desktop) or All devices (mobile).
- **Tested site:** `NEXT_PUBLIC_SITE_URL`, else Vercel's production domain
  (`VERCEL_PROJECT_PRODUCTION_URL`). Local and private addresses are skipped: Google can't reach
  them (`src/integrations/site.ts`).
- **Setup:** `GOOGLE_API_KEY`, an API key whose Google Cloud project has the PageSpeed Insights API
  and the Chrome UX Report API enabled. Calls come from the server, so set the key's application
  restriction to None and restrict it to those two APIs, or allow the site's domain under website
  restrictions (requests name the site as their referrer).
- **Errors:** Google's reason (`error.details[].reason`) becomes a message, plus a link for
  administrators to fix it: an API that isn't enabled, an invalid key, website, IP or API
  restrictions, an exhausted quota, or a page Lighthouse couldn't load (down, an error status, or
  behind Vercel Deployment Protection).
- **Layout:** each part is a size container, so gauges, metrics and table columns follow the
  widget's width, not the viewport's.
- **History (E4b):** the `pagespeed-report` job stores a Lighthouse run for phones and desktops
  every day in `pagespeed-reports` (90 days). Under the lab test the widget draws the performance
  score of the stored runs as a sparkline (`StoredHistory`), with the change over the window and
  the best and worst score written as text. **Run again** (Scheduled jobs capability) runs the job
  through `POST /api/jobs/run`; the endpoint expires the `pagespeed` cache tag afterwards, so the
  live lab test also runs again on the next render.

## Media

- **Sizes.** Every upload generates three derivatives with sharp (`src/collections/Media.ts`):
  `thumbnail` 400×300 (admin lists, drawers and relationship pickers only), `card` 800×500 (article
  and project cards) and `og` 1200×630 (Open Graph and Twitter cards). A picture smaller than a
  target gets no file for that size (Payload's default `withoutEnlargement`), which is why the
  mappers always fall back to the original. Article metadata uses `og` when it exists, the original
  cover otherwise, and the profile photo only when the article has no cover at all.
- **Focal point.** Enabled on the collection: the editor clicks the part of the picture that must
  stay in frame, and every crop without an explicit `position` keeps it. `thumbnail` still crops from
  the centre because it is an admin-only square-ish preview.
- **Accepted types.** `image/*` plus `application/pdf`, for documents such as a CV. Payload does not
  resize PDFs; they keep the original only.
- **Regeneration.** `pnpm media:regenerate` re-uploads every original from `media/` (or `MEDIA_DIR`)
  through Payload, which writes any size the document is missing — use it after adding a size so
  files uploaded earlier catch up. `--dry-run` lists the documents without writing, `--only=og`
  prints a reminder of the size you meant to check. Originals missing from the upload directory are
  reported and skipped, never deleted. Size files whose size no longer exists stay on disk; remove
  them by hand if disk use matters.

### Folders (beta)

`folders: true` on Media turns on Payload's beta folder feature. The sidebar gains **Browse by
Folder** (`/admin/browse-by-folder`), where the library is grouped by where an image is used; the
seed creates *Project covers*, *Article covers* and *Certificates* and files each upload into its
folder. A media document carries a hidden `folder` relationship, and folders can be nested.

  the API works with just a name. Add `admin.hidden: false` back — or drop the override — when a
  second collection enables folders.
- **Schema.** Payload adds the hidden `payload-folders` collection, the join table for its type, the
  `media.folder_id` column and a row in the lock table. `20261021_163000_media_folders` creates them
  (hand-written: the schema diff cannot be generated non-interactively after the orderable
  migrations), and the folder collection is cleared after `media` in the seed.
- **Accessibility.** Payload's folder view ships three gaps that the admin's gate caught: the
  grid/list toggles and the folder "…" menu are icon-only buttons with no label, the card
  thumbnails have no `alt`, and the "Create folder" control is a `<div type="button">`. The DOM
  fixes name them and make the create control a real button (see `docs/ui-modernization/a11y.md`);
  the section titles and the "Media" chips use the muted token because Payload's own colours fall

  folder, and both folder surfaces are part of the axe sweep.
- **Beta caveat.** Payload labels folders beta; the collection slug (`payload-folders`), the field
  name (`folder`) and the route are Payload's defaults so a later release can change its internals
  without a config migration here. `debug: true` in the root config would reveal the hidden
  collection and fields; it stays off.

### Orderable lists

Every ordered collection opts into Payload's drag-and-drop ordering with `orderable: true`
(experimental in Payload 3.90, so the API may change in a minor release): **Skills** (the pilot),
**Educations, Experiences, Projects and Services**. The manual `order` number and `src/fields/order.ts`
are gone:

- Payload adds a hidden, read-only `_order` text field holding a fractional index, a `beforeChange`
  hook that appends each new document, and a `/api/<collection>/reorder` endpoint the list calls on
  a drop. Only the moved document is written.
- The list is Payload's own (the TanStack view steps aside for orderable collections), so it gets
  the drag handles, and `defaultSort` is not needed — the list sorts by `_order`.
- Queries that feed the site sort by `_order` too (`src/app/(frontend)/lib/payload-source.ts`).
- Seed data is created one document at a time; parallel creates would each read the same "last"
  key and land in an arbitrary order. Projects prepares its images in parallel but creates the
  documents sequentially for the same reason.
- Migrations `20261021_001500_skills_orderable` and
  `20261021_150000_orderable_profile_and_services` backfill `_order` from the old numeric `order`
  and `id` (`lpad((order * 100000 + id), 11, '0') || '1'`, a key that sorts like the numbers and
  does not end in `0`), then drop the column. Both are reversible.
- `tests/int/orderable.int.spec.ts` runs append, sort, hidden-field and schema assertions for all
  five collections and checks the frontend queries; `tests/e2e/orderable.e2e.spec.ts` drags a row
  with pointer events (dnd-kit ignores HTML5 drag events) on Skills and Experiences, and checks the
  handles and absence of the numeric column on all five.

To make a new collection orderable: add `orderable: true`, remove the `orderField`, `defaultSort`
and the `order` column from `defaultColumns`, switch its frontend query to `sort: '_order'`, create
its documents sequentially in the seed, and add a migration that backfills `_order` the same way.

## Responsive layout

Audited in Chrome with mobile emulation at 360×740, 390×844, 844×390, 768×1024, 820×1180 and
1024×768 (`tests/e2e/responsive.e2e.spec.ts` checks a phone and a 768px tablet). Fixes live in
`src/styles/admin/responsive.css`, plus Tailwind `max-sm:` and `pointer-coarse:` classes.

Breakpoints: phone rules use `max-width: 768px`, Payload's own small break. At exactly 768px
(iPad mini portrait) Payload already switches to its phone layout, so rules that stopped at 767px
left that width broken (header actions off screen, count cards one per row). "Touch" below means
`(pointer: coarse)`.

- **Header:** up to 1024px the actions keep their size and the breadcrumbs take what is left,
  ending in an ellipsis. Payload caps the actions at 150px (300px up to 1024px), less than search,
  developer tools, theme and account need. On phones the GraphQL button hides; the developer tools
  menu links to the playground and opens as a full-width sheet under the header. Payload's header
  gradient overlay no longer catches taps (it blocked the account menu). Touch screens hide the
  search button's Ctrl K hint.
- **Browser toolbar:** `ThemeToggle` renders `<meta name="theme-color">` (React puts it in the
  head) with the page background of the current theme, so Chrome on Android and Safari tint their
  toolbar to match, and it changes with the theme switch.
- **Sidebar:** Payload's overlay menu below 1025px, with the same icons and colours; the rail
  toggle is desktop only.
- **Dashboard:** count cards two per row on phones and four per row from 600px to 768px. Payload
  forces widgets to `width: 100% !important` there, which a later layer can't override, so the
  dashboard becomes a grid instead (count cards one cell, other widgets the full row; not while
  editing the layout).
- **Documents:** on phones the title wraps to two lines at 24.5px instead of one cut-off line.
  Payload keeps "Last modified / Created" as a strip that scrolls sideways, with a fade.
- **Lists:** cells wrap, so titles are readable; the table still scrolls sideways for more columns
  above 640px. The bulk actions bar spans the screen and wraps (Delete used to end off screen).
- **Lists on phones (below 640px): cards.** Each row becomes a card: the checkbox and the first
  visible column form the title line, and every other column shows as a label and value line. The
  header row turns into wrapping sort chips (Payload's sort arrows still work). Tapping anywhere on
  a card opens the document (the title link stretches over the card; the checkbox and any other
  control stay on top), and the card darkens while pressed. It is CSS only, in the
  `@layer utilities` block of `responsive.css`: `DataTable` puts `data-label` (the column's label)
  and `data-primary` (the title cell) on each cell and keeps explicit table roles, since
  `display: grid` on a table drops them in some browsers. Hiding or reordering columns changes the
  cards too.
- **List accessibility:** Payload's row checkboxes have an empty `aria-label`, so `DataTable` wraps
  them in a label ("Select" plus the row title). Payload's sort arrows get 24px targets on every
  screen.
- **Text sizes:** nothing in the admin is smaller than 12px (the text scale in `admin-ui.css` is in
  px; avoid `rem` in arbitrary values, since the admin's rem is 14px). Form fields on touch screens
  use 16px text: iPhone browsers, Chrome included, zoom into any field under 16px when it gets
  focus. That covers Payload's inputs, textareas, selects, react-select, the rich text editor,
  list search and the admin's own inputs (`!important`, because Payload, react-select and Tailwind
  utilities all set smaller sizes; the header's breadcrumb select is left out). Phones in landscape
  don't inflate text (`-webkit-text-size-adjust`).
- **Menus:** on touch screens menu rows are at least 40px tall: the header's account, developer
  tools and Create menus, Payload's popups (document and array row actions, per page) and
  react-select options. Payload's popups then get more height before they scroll, because their
  scrollbar is hidden and the last action ("Remove") would sit out of sight. Closed header menus
  are `display: none` (`[details:not([open])>&]:hidden`): Chrome still laid out the closed panels,
  which widened the page on phones. The developer tools menu fits the screen with `dvh` and keeps
  its scrolling to itself (`overscroll-contain`).
- **Command menu on phones:** it opens at the top of the screen, full width, and its height follows
  the visual viewport (`useVisibleHeight`), so the on-screen keyboard no longer hides the last
  results. Touch screens hide the keyboard hints.
- **Touch targets:** sidebar group headings and breadcrumb links get at least 24px (WCAG 2.5.8).
  Payload's small icon buttons (array row actions, copy, remove chip), "Collapse all", "Show all"
  and per page get 32px. The date picker gets 35px days with 14px numbers and month arrows with a
  40px hit area; its clear button gets a 32px hit area without moving (both through transparent
  pseudo elements, since Payload draws the arrows as CSS triangles in a fixed box). Recent changes
  rows are tappable over their full height.
- **Sideways scroll fixes:** Payload's mobile sidebar header was `100vw` wide (scrollbar included):
  20px of sideways scroll at 1024px; it is `100%` now. The dividers around "Payload Settings" on
  the account page were 100% + 100px wide: 68px of sideways scroll on a phone; they are full bleed
  now. The e2e check measures the page against the visual viewport: with mobile emulation, a wider
  page widens `innerWidth` along with it, so comparing with `innerWidth` never failed.

## Live Preview

The article edit view has Payload's Live Preview toggle. The iframe opens `/preview/articles/[slug]`
(a dynamic, `noindex` route) — not the public article page:

- The public page is prerendered from `generateStaticParams` and only knows published articles.
  Pointing Live Preview at it meant a draft's preview landed on "Article not found".
- The preview route renders the published article when there is one, and an otherwise empty article
  page for a draft. `ArticleLivePreview` (loaded only inside a frame, as its own chunk) fills that
  from the editor's form state, which Payload posts on load and on every change.
- The relationships the preview needs are fetched through Payload's REST API with the editor's own
  session, so access control still decides what may be seen: for anyone who is not signed in, a
  draft stays invisible and the route shows only the shell.

`Articles.admin.livePreview.url` builds the address (`?id=<doc id>` lets the preview resolve the
cover image); articles without a slug or a body get no preview.

## Trash (soft delete)

- On Articles, Projects, Services, Experiences, Educations, Certificates, Skills and Media
  (`trash: true`). Deleting moves documents to the collection's **Trash** tab
  (`/collections/<slug>/trash`), where they are read-only and can be restored. Normal queries,
  the public site and the dashboard leave trashed documents out.
- Access (`contentAccess` in `src/access/roles.ts`, ADR 0011): users whose role gives Edit can
  move documents to the trash and restore them; deleting permanently ("Delete permanently",
  "Empty trash", the "skip trash" option) needs Full. Payload computes the two permissions
  separately, so an Edit user sees Delete and Restore but no permanent delete.
- Trashing is an update, so the `afterChange` hooks run and the site cache is refreshed;
  `afterDelete` runs only on permanent deletes. A trashed media file stays in storage until it is
  deleted permanently.
- The list summary links to the trash when it holds documents ("2 in the trash"); on the trash
  view it says what can be done there.
- Not combined with Payload folders yet: the folder view's delete skips the trash dialog
  (payloadcms/payload#16327).

## Drafts and scheduled publishing

Articles keep versions with drafts (`versions: { drafts: true, maxPerDoc: 20 }`). The publish
controls in the edit view are Payload's own: **Save Draft** keeps the article editable and invisible
to the public site, **Publish** (or **Publish changes**) makes it live.

- **Public reads skip drafts.** Anonymous REST reads get `_status = published` from
  `Articles.access.read`; the frontend queries in `src/app/(frontend)/lib/payload-source.ts` add the
  same condition, because the Local API bypasses access control (`overrideAccess` defaults to true).
  A draft therefore 404s and stays out of lists, the sitemap and the home page.
- **Scheduled publishing.** The `publishAt` date field (sidebar, only while the article is not
  published) is read by the `publish-scheduled` daily task: it finds drafts whose `publishAt` has
  passed and publishes each one with its own field values. Payload's core `schedulePublish` job
  (`versions.drafts.schedulePublish`) is not used — the task registry is the project's own
  scheduler, so admins see the run, its log and its result in Admin › Scheduled jobs like any other
  task. A status-only update would publish stale content, because Payload merges `data` over the
  published document rather than over the latest draft.
- **Trash and restore.** Payload restores as a **draft** when the collection keeps drafts; the
  restore dialog has a "restore as published" box for the editor who wants the article back on the
  site.
- **Cache invalidation.** Saving in the admin runs the collection hooks, which expire the portfolio
  cache tag and the affected paths. The publish task runs inside a job, where there is no request
  store, so the jobs endpoint expires the tag and the published article paths itself when the run
  finishes.
- Migration `20261020_231332_drafts_and_scheduled_publishing` creates the versions table, adds
  `_status` (default `draft`) and `publish_at`, makes title/excerpt/publishedAt/link nullable for
  drafts, and **backfills every existing row to `published`** — without that, enabling drafts hides
  all existing content.

## SEO metadata

Payload's SEO plugin (`@payloadcms/plugin-seo`, wired in `src/plugins/seo.ts`) adds a **meta**
group to Articles and the Site settings global: a title, a description and an image, each with an

- **Drafts.** Articles keep versions, so the group's columns exist twice: `articles.meta_*` on the
  published row and `_articles_v.version_meta_*` on each version. A preview of a draft shows the
  draft's metadata.
- **`tabbedUI` is off.** With it on, the plugin moves every field into a new "Content" tab, which
  drags the sidebar fields (slug, category, publish date) into the main column. With it off the
  group is appended below the body.
- **Admin fixes.** The plugin renders its widgets with inline styles: instruction lines at
  `#9A9A9A` (2.6:1), white text on red/orange/green pills (1.9–4:1), and a non-interactive mock

- **Crawlability.** `/sitemap.xml` lists the home page and every article that has a page — slug and

## Scheduled jobs

Admin › **Scheduled jobs** (`/admin/jobs`, `views/Jobs`, the `manageJobs` capability) runs the
maintenance tasks the CMS needs and shows when each one ran and what it found. The tasks live in
`src/jobs`:

| Task | Schedule | What it does |
| --- | --- | --- |
| `trash-cleanup` | daily | Permanently deletes documents that have been in the trash longer than `TRASH_RETENTION_DAYS` (30), on every `trash: true` collection. Media files go with their documents. |
| `pagespeed-report` | daily | Runs Lighthouse for phones and desktops through PageSpeed Insights (in parallel) and stores both runs in `pagespeed-reports`. Needs `GOOGLE_API_KEY` and a public site address. Keeps 90 days. |
| `publish-scheduled` | daily | Publishes draft articles whose *Publish at* has passed, so a scheduled article goes live within a day (one cron call per day on Hobby). Running it by hand publishes immediately. |
| `broken-links` | Mondays | Crawls the home page and every article page, collects their links and requests each one (HEAD, then GET when a server refuses HEAD). Reports the broken ones with the page they were found on. Up to 60 links per run. |
| `database-upkeep` | Sundays | `ANALYZE`s the tables that have rows but no statistics, `VACUUM ANALYZE`s those with more than 1 000 dead rows, and moves any ID sequence that fell behind its highest id. Leaves orphaned rows and invalid indexes to the database page, where they are reported but not applied, and skips tables over 200 MB so a run fits in one request. |

How a run happens:

- **The queue is the `job-runs` collection** (`src/collections/Jobs.ts`, hidden from the sidebar).
  A run is created as `queued`, becomes `running`, then `done`, `failed` or `cancelled`, with its
  summary, error, duration, log (last 20 kB) and task details (counts, broken links).
- **Vercel Cron** calls `GET /api/jobs/cron` once a day (`vercel.json`). The endpoint requires
  `Authorization: Bearer $CRON_SECRET` and answers 503 while `CRON_SECRET` is unset, so it can never
  run unauthenticated. It queues the tasks that are due today and drains the queue in one request.
- **Run now** (`POST /api/jobs/run`, signed in + `manageJobs`) queues one task and runs the queue
  immediately. A task that is already queued or running returns 409 instead of running twice.
  **Cancel** (`POST /api/jobs/cancel`) cancels a queued run before its turn; a run that has started
  cannot be interrupted, because the function is the worker.
- A run whose function died (a deploy, the 60 s limit) is marked failed after 15 minutes
  (`STALE_RUN_MS`) by the next queue call, so the task is not blocked forever.
- The collection slug is `job-runs`, not `jobs`: Payload resolves `/api/jobs/:id` as a collection
  before the custom endpoints, which would shadow `/api/jobs/cron`.

Adding a task: a file in `src/jobs/tasks` exporting a `JobTask` (`slug`, `label`, `description`,
`schedule`, optional `weekday`, `needs`, `run`), then an entry in `TASKS`
(`src/jobs/registry.ts`). The jobs collection options, the page and the cron endpoint read that
list, so nothing else changes; run `pnpm generate:all` for the new select option, then
`pnpm typecheck && pnpm test:int`. `tests/int/jobs.int.spec.ts` covers the queue, the permanent
deletion, the cron secret and the access rules.

## Component tests

`tests/unit/admin-components.spec.tsx` covers the primitives the admin is built from, with Testing
Library and jsdom: the element a primitive renders (a `button` that refuses clicks while disabled,
a `span` that becomes a link through `render`), the ARIA state of the tab list, toggle group and
progress bar, a dialog that opens from its trigger, names itself and returns focus on Escape, and
the two status components' text. They run in the same Vitest pass as the integration tests
(`pnpm test:int`; `pnpm test:unit` for just these), with `// @vitest-environment jsdom` at the top
of the file, because the default environment is node (see `vitest.config.mts` for why).

Rules of thumb:

- Test behaviour that a Payload or Base UI upgrade could break, not classes. The one class
  assertion per primitive is there to catch a variant being dropped, not to freeze the design.
- Keep admin components React-only here. A component that pulls in `@payloadcms/ui` (fields that
  call `useField`, anything with Payload's CSS) cannot load in Vitest — the CSS import throws. Those
  are covered by the e2e suites instead; the pure parts are split into their own modules (see
  `AdminDomFixes/landmarks.ts` or `PaginationLabels/labels.ts`) precisely so they can be tested
  this way.
- Popups that need layout (tooltips, because Base UI measures the trigger) are not testable in
  jsdom; the axe e2e checks them in a real browser.
- Testing Library cleans up between tests only when the framework provides global `afterEach`, and
  this project keeps Vitest globals off: the file calls `afterEach(cleanup)` itself.

## Acceptance tests (editor tasks)

`tests/e2e/acceptance.e2e.spec.ts` measures the three tasks an editor does most often, rather than
checking one screen:

| Task | What it does |
| --- | --- |
| `publish-article-with-cover` | Writes an article, adds a cover through the media drawer (file + alt text) and publishes it, then reads it on the public site with the cover rendered. |
| `draft-then-publish` | Saves an article as a draft, checks the public site still answers 404, then publishes the same document. |
| `replace-cover-with-external-url` | Finds an article in the list, removes its media file, switches to the URL tab and saves the external URL (the file wins while it is attached, so both steps are the real workflow). |

Each task runs through `TaskMeter` (`tests/helpers/measure.ts`), which counts one step per editor
action (open a screen, type a field, click a button, choose a file) and times the task against the
production build. The numbers are compared with `tests/acceptance-baseline.json`: steps may grow by
two, time by 60% plus two seconds. The point is the diff — when a redesign adds clicks to a routine
task, the baseline has to change in the same commit, so the cost is visible in review. Every run
also writes `test-results/acceptance.json` and adds an `acceptance` annotation to the test, so the
numbers appear in the report without reading logs.

Re-record the baseline after an intentional UX change:

```bash
rm tests/acceptance-baseline.json && pnpm test:e2e --grep "Editor acceptance tasks"
cat test-results/acceptance.json   # then copy steps/ms into tests/acceptance-baseline.json
```

## Audit log

Admin › **Audit log** (`/admin/collections/audit-logs`, the `viewAuditLog` capability) lists who
created, changed, trashed, restored or permanently deleted a document, and who signed in or out.
The dashboard's **Audit log** widget shows the same entries, newest first.

- **Every content collection and global is audited automatically.** `auditLogPlugin`
  (`src/plugins/auditLog.ts`) appends `afterChange` and `afterDelete` hooks to each collection and
  an `afterChange` hook to each global; auth collections also get `afterLogin`/`afterLogout`. A new
  collection therefore needs no audit code. Opt out with `custom: { audit: false }` on the entity,
  or `context: { skipAudit: true }` on a Local API call (the seed uses this).
- **The entries are append-only.** `src/collections/AuditLogs.ts` allows reads with the capability
  and denies create, update and delete to everyone; only the server writes, through the Local API
  with `overrideAccess`. There are no drafts and no trash.
- **The change list is safe and small.** `src/audit/record.ts` compares the top-level fields of the
  previous and new document, keeps at most 25 fields and 160 characters per value, and never records
  names that look like secrets (`password`, `salt`, `token`, `apiKey`, …). The account is stored as
  an id and an email snapshot, not a relationship, so an entry survives deleting the account.
- **Writes join the caller's transaction.** The recorder passes the caller's `req`, so a
  rolled-back change leaves no entry, and the insert cannot deadlock on a row the change still
  holds. A failed log write is logged and never fails the content change.
- **Payload's list does the filtering.** The collection sets `listSearchableFields`
  (`summary`, `documentTitle`, `userEmail`, `entity`) and default columns, so search, filters,
  sorting and pagination are Payload's own; the sidebar entry is hidden from users without the
  capability.

Adding a capability-guarded tool: add its name to `CAPABILITIES` (`src/access/permissions.ts`), use
`hasCapability(req.user, '…')` in the view and `capabilityAccess('…')` in a collection's access, add
the link to `NavExtraLinks` when it has a page of its own, and add it to the role form — the form is
generated from `CAPABILITIES`. A tool that should be reusable elsewhere is a plugin instead:
`manageDatabase` comes from `DATABASE_TOOLS_CAPABILITY` (re-exported by the database tools plugin),
which the Roles form lists like any other entry, and the plugin registers its own view, link and
endpoints; see [docs/plugins/database-tools.md](../plugins/database-tools.md).

## Database page

Admin › **Database** (`/admin/database`, `views/Database`, the `manageDatabase` capability) is the
operational view of the tables. It is separate from **System** on purpose: System reads a snapshot
with the Payload adapter (`viewSystem`), while this page opens its own `pg` connection
(`src/plugins/databaseTools/server/connection.ts`, `DATABASE_DIRECT_URL` or `POSTGRES_URL`) because
maintenance cannot run through a single-query adapter.

The page, its endpoints and its sidebar link come from one plugin call,
`databaseTools({ access, audit, migrations })` in `src/payload.config.ts`; the plugin packages the
tools so another Payload project can mount them. See
[docs/plugins/database-tools.md](../plugins/database-tools.md) for the options, the endpoints and
how the capability is granted.

| Card | What it does | Where the SQL lives |
| --- | --- | --- |
| Connection | Server version, size, connections, cache-hit ratio, uptime, and whether the URL is a pooled serverless endpoint. | `server/introspection.ts` |
| Backup | Download a `.sql` dump (whole database, the browsed table, or schema only) or a `.json` description. | `server/backup.ts` |
| Tables | Every `public` table with row estimate, size (heap and indexes apart), dead rows and last vacuum; **Browse** opens columns, primary key, indexes, constraints, the table's DDL, the query plan for the current filter/sort and a page of 25 rows, with a filter bar (`f=column:operator:value` in the URL, so a filtered view is a link), sortable column headers, and **Export CSV** of exactly what is on screen. Read-only. | `server/introspection.ts`, `server/filters.ts` |
| Sessions and locks | Live `pg_stat_activity`: active/idle/idle-in-transaction counts, statements running longer than 30 s, and `pg_blocking_pids` for who waits on whom. **Cancel query** (`pg_cancel_backend`) keeps the connection; **End session** (`pg_terminate_backend`) rolls the transaction back and needs the pid typed. The page's own connection is labelled and cannot be targeted. | `server/sessions.ts` |
| Maintenance | `ANALYZE`, `VACUUM`, `VACUUM ANALYZE`, and `REINDEX CONCURRENTLY` of every invalid index — on the whole database or the browsed table. | `server/maintenance.ts` |
| Health and repair | Seven checks (migrations, sequences, relation rows, indexes, statistics, dead rows, primary keys) and the four that are safely fixable: `setval`, `DELETE` orphans, `REINDEX`, `ANALYZE`. | `server/repair.ts` |
| Neon branches | With `NEON_API_KEY`: create a branch at this moment, list branches, delete a backup branch, and restore the branch to a timestamp with the current state kept under a name. | `server/neon.ts` |
| Restore | Choose a `.sql` file, **Check the file** (statements, tables, existing content, whether it is transactional), then type `restore` to run it. | `server/restore.ts` |

Decisions worth knowing:

- **The dump is generated by Postgres.** `format('%L', column)` renders every value with its own
  type's rules, so enums, `timestamptz`, `jsonb`, arrays and `bytea` round-trip; nothing is
  serialised through JavaScript. Order: types, sequences, tables, keys, data, indexes, foreign keys
  (last, so rows can reference rows inserted later). The file has `BEGIN`/`COMMIT`, so a failure
  rolls back; `pnpm db:restore <file> --yes` is the CLI that runs it.
- **Locks and preferences keep their tables but not their rows.** Restoring a stale
  `payload_locked_documents` row would make a document impossible to edit. `payload_migrations` *is*
  included, so a restored database knows its migration state (`pnpm db:status` says `ready`).
- **Restoring is refused unless it is confirmed.** The endpoint inspects the file (it may not touch
  the server: no `DROP DATABASE`, `ALTER SYSTEM`, roles or psql meta-commands) and refuses when the
  content tables hold rows unless the request carries the typed confirmation; the CLI asks for
  `--yes` the same way. `RestoreRefused` carries the status, so the page gets 400/409 rather than a
  500 for something the admin can fix.
- **Cancel before terminate.** A cancel stops one statement and the client can retry; terminating
  ends the session and rolls back its transaction, so it is the right tool only for an
  `idle in transaction` session (which has no statement to cancel) and it needs the pid typed.
- **No row editing.** A cell editor here would bypass validation, the audit log and cache
  revalidation, so the browser is read-only and links the collection instead.
- **Not offered:** `VACUUM FULL` (locks the table for the whole rewrite), `CREATE`/`DROP DATABASE`
  and roles (a serverless role cannot, and one connection names one database), and anything that
  needs `psql`/`pg_dump` (the server may not have them).
- **Neon is the control plane, not SQL.** A branch and its history are project storage, so backup,
  point-in-time restore and deletion go through `https://console.neon.tech/api/v2` with
  `NEON_API_KEY`. The project is found by matching this database's compute endpoint to the projects
  the key can see (the `-pooler` suffix is stripped); `NEON_PROJECT_ID`/`NEON_BRANCH_ID` skip that.
  Without a key the card explains the two variables and links the console; the endpoints answer
  `501`, not a permission error.

Every endpoint (`src/plugins/databaseTools/endpoints.ts`) answers `403` without the capability,
logs through Payload's logger, writes restores, maintenance and branch changes through the plugin's
`audit` sink (the app's audit log), and returns a one-line explanation — never a stack trace, a
query, or a connection string. The page's data functions are covered live in
`tests/int/database-tools.int.spec.ts`; the Neon client is tested against a fake `fetch` that
asserts paths and bodies, and the plugin's contract (options, defaults, what it registers) in
`tests/int/database-tools-plugin.int.spec.ts`.

## Terminal (development only)

Admin › **Terminal** (`/admin/terminal`, `views/Terminal`, the `useTerminal` capability) runs one
of the project's package scripts and streams its output. A production build answers 404 on the page
and on the endpoint, whatever the user's roles.

- **The allow-list is code.** `src/terminal/scripts.ts` declares each slug, label, description,
  `pnpm run` arguments and timeout. The browser posts a slug to `POST /api/dev/terminal`; the
  endpoint (`src/endpoints/devTerminal.ts`) looks it up, spawns `pnpm` without a shell in the
  repository root and streams stdout/stderr as `text/plain`. Time out and browser disconnects kill
  the process (`SIGTERM`, then `SIGKILL`).
- **What is on the list:** lint, typecheck, the two admin checks, `generate:all` (marked as writing
  files), `migrate:status` and `test:int`. The dev server, the build, `seed` and `migrate` are
  deliberately absent.
- **The console is a lazy client chunk** (`TerminalLazy` → `Console.tsx`), so Payload's single admin
  route does not ship it to every page. Output is plain text in a `<pre role="log">`.
- **Security review:** [terminal-security.md](./terminal-security.md) (threat model, controls,
  residual risks, checklist). The unit tests in `tests/int/terminal.int.spec.ts` assert the
  allow-list shape and the production gate; `tests/e2e/terminal.e2e.spec.ts` runs a script in
  development and skips in the CI production build.

## GraphQL document tab

Every collection and global has a **GraphQL** tab next to Payload's **API** tab
(`views/GraphQL`, a custom document view added by `adminUIPlugin` as `views.edit.graphql`, tab
order 450; opt out with `custom: { graphqlTab: false }`). It works like the API tab:

- The same options: **Draft** (when drafts are on), **Authenticated** (sends the session cookie or
  not), **Locale** (when localization is on) and **Depth**.
- The server builds the query from Payload's own GraphQL schema (`configToSchema`, the schema
  `/api/graphql` serves, cached per config): every field of the document, groups, arrays and blocks
  expanded, relationships expanded to the chosen depth (at 0 they select only `id`, the GraphQL
  equivalent of REST's `depth`). Depth goes up to 5.
- The client (a lazy chunk) runs it with `POST /api/graphql` and shows the query, the variables
  (`id`, and `draft`, `locale` or `trash` when they apply), the response with its status and time,
  copy buttons for the URL, the query and a cURL command, and a link to the GraphQL Playground
  where Payload serves it.
- Hidden where the API tab is hidden (`admin.hideAPIURL`) and when GraphQL is off
  (`graphQL.disable`, or `graphQL: false` on the collection or global).

## Roles and permissions

Admin › **Roles** (`src/collections/Roles.ts`, ADR 0011) is where access is managed:

- A role gives an **access level** per collection and global (No access, Read only, Edit, Full;
  globals stop at Edit), **capabilities** for the tools (traffic, deployments, audit log, jobs,
  system, database tools, developer tools, terminal), or **Full access**. The level rows are
  generated from the config, grouped like the sidebar; a new collection gets its row automatically
  (opt out with `custom: { permissions: false }`).
- Users get roles on their account (`users.roles`, administrators only). With several roles the
  highest level and every capability apply. Users without a role can't open the admin.
- The roles list starts with an **access overview** (collections and tools down, roles across).
  The role form lists its members (a join field).
- Built in: **Administrator** (full access; can't be deleted or lose full access) and **Editor**
  (Edit everywhere, traffic and deployment widgets, given to new users). The first user is an
  administrator; the last administrator can't be demoted or deleted.

In code, read permissions from the user, never from role names:

```ts
import { can, hasCapability, isAdmin } from '@/access/permissions'

can(req.user, 'articles', 'update') // access level allows the operation
hasCapability(user, 'viewAuditLog') // a tool
isAdmin(user) // full access
```

`user.permissions` is a virtual field merged from the roles on every read, so it is current in
access functions, server components and client components (`useAuth().user`). Collection configs
use the factories in `src/access/roles.ts`: `contentAccess(slug)`, `globalAccess(slug)`,
`hiddenWithout(slug)` for `admin.hidden`, `capabilityAccess(capability)`, `adminsOnly`. Behaviour
is covered by `tests/int/roles.int.spec.ts` and `tests/e2e/roles.e2e.spec.ts`.

## Checks

```bash
pnpm typecheck          # TypeScript
pnpm lint               # ESLint
pnpm check:tw-prefix    # admin classes carry the acn: prefix
pnpm check:contrast     # token pairs meet WCAG AA in both themes
pnpm test:int           # Vitest: Local API integration + admin component tests (jsdom)
pnpm test:unit          # only the component tests, for a focused loop
pnpm test:e2e           # Playwright: admin, navigation, dashboard, lists, gallery (axe), editor tasks
pnpm test:invariants    # the platform-independent half of the visual gate (runs in CI)
pnpm test:visual        # screenshot comparisons + the invariants, on the machine with the baselines
```

`tests/visual/invariants.visual.spec.ts` is the half of the visual check that is the same on every
machine, so CI gates on it: the design tokens load (14px body text, `--theme-elevation-0`
resolves), no screen scrolls sideways at 1440/768/375px in either theme, every thumbnail loads, dark
mode is still the navy tint, and the dashboard keeps its heading and widget cards. Together with the
axe suites, that means a screen that "looks broken" fails CI even where pixel diffs would be
platform noise. Screenshot comparisons stay on the machine that owns the baselines
(`pnpm test:visual --update-snapshots`), and CI uploads captures plus
`test-results/visual-invariants.json` for review.

`tests/e2e/a11y.e2e.spec.ts` is the accessibility gate: axe against the WCAG 2.2 AA tags on
fourteen admin surfaces in both themes, plus the structure axe cannot see (one main landmark, one
`<h1>`, title, language, and a skip link that is the first tab stop and moves focus to main). It
runs in CI with the rest of `pnpm test:e2e` and writes `test-results/a11y-<theme>.json`. The
allowlisted upstream findings, the fixes made for them and the manual screen-reader checklist are
in [`a11y.md`](./a11y.md). The older per-feature axe checks (component gallery, command menu, tile
pickers, audit log, jobs, system, terminal) still run alongside it. Performance budgets and how to
measure them are in [`perf-budget.md`](./perf-budget.md).

### Running Playwright where browsers are not installed

`sandbox` images can lack Playwright's browser download and the system libraries Chromium needs.
`@sparticuz/chromium` ships a compatible binary plus the Amazon Linux 2023 NSS libraries:

```bash
npm i @sparticuz/chromium                     # outside the repo, e.g. /tmp/chrome
node -e "import('@sparticuz/chromium').then(async (m) => console.log(await m.default.executablePath()))"
# /tmp/chromium, and /tmp/al2023/lib now holds libnspr4, libnss3, ...
LD_LIBRARY_PATH=/tmp/al2023/lib PLAYWRIGHT_CHROMIUM_EXECUTABLE=/tmp/chromium pnpm test:e2e
```

`playwright.config.ts` already honours `PLAYWRIGHT_CHROMIUM_EXECUTABLE`. With
`PLAYWRIGHT_BASE_URL=http://localhost:3000` and `CI=1` the suite runs against a production build
(`next build` + `next start`) instead of the dev server; seed first (`pnpm seed`) — several suites
assume the demo content exists. Tests that need the development-only terminal skip themselves when
the production gate answers 404.

## Known upstream gaps

Payload 3.90 has a few admin gaps this project works around. Each one has a test, so an upgrade
that fixes it upstream is noticed rather than silently double-fixed.

- **Pagination arrows have no accessible name.** `ClickableArrow` renders a `<button
  class="clickable-arrow clickable-arrow--left|right">` with an SVG and no text, so axe reports
  `button-name` (critical) on every paginated list, the media drawer and the relationship pickers.
  There is no config slot for the paginator, so `providers/AdminDomFixes` labels the buttons in the
  DOM (`aria-label="Previous page"`/`"Next page"`), and only when a button has no name yet — a
  future Payload version that ships its own label wins. Covered by
  `tests/e2e/a11y.e2e.spec.ts`; drop the module once Payload labels the arrows.
- **The dashboard and list templates have no `<main>` landmark, and the shell has no skip link.**
  Document views render their own `<main>`; the dashboard and every list render a `<div>` after the
  header. `providers/AdminDomFixes/landmarks.ts` marks the view as `role="main"` (or reuses the
  page's `<main>`) and inserts the skip link. The dashboard and sign-in screens also had no `<h1>`;
  `views/PageTitle` supplies one through `beforeDashboard`/`beforeLogin`.
- **Payload's select decorations are `aria-hidden` but focusable.** `.dropdown-indicator` and
  `.clear-indicator` are taken out of the tab order by the same component, and the icon-only
  document controls (the "…" menu, edit/remove on an upload, clear on a date field) are named there
  because Payload passes no label. The row-selection checkboxes had `aria-label=""` and are named
  too; the full list, with the rules that are allowlisted instead, is in [`a11y.md`](./a11y.md).
- **A screen-reader-only (`acn:sr-only`) span inside a truncated line anchors to the page.** The
  span is `position: absolute`; without a positioned ancestor it lands at its static position and
  widens the document on phones (the responsive test measures `scrollWidth`). Any truncated element
  that contains sr-only text therefore carries `acn:relative` (`widgets/Deployments`,
  `widgets/CIStatus`, `widgets/PageSpeed`).
- **Payload's list toolbar search input is a text field, not a `searchbox`.** Tests look for
  `getByRole('textbox', { name: /Search by/ })`.
